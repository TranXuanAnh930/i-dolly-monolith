<a id="concurrency"></a>
**並行性 — お金や在庫が関わるすべての箇所で再利用する、単一の行ロックパターン。**
購入手続き（`order_service.checkout`）、チケット購入（`ticket_service.checkout_ticket`）、抽選処理
（`lottery_draw_service.draw_lottery`）はすべて同じ形に従います: 処理が読み取ってから書き込むすべての行に
`with_for_update()` のロックを取得し、*ロックを保持したまま* ビジネスルールをチェックし、書き込みを行い、
最後にちょうど 1 回だけコミットします — 途中でコミットすることは決してなく、書き込みが完了するまでに
変わり得る条件をロック前にチェックすることもありません。購入手続きの経路では、影響を受けるすべての
`Product` 行を固定の順序（主キー順）でロックします。これは、重なりのあるカートを扱う 2 つの同時購入が、
同じ 2 行を逆の順序で取得して互いにデッドロックすることを防ぐためです。

抽選キャンペーンが *変わらないこと* だけを必要とする処理は、より弱いロックを取得します。抽選への応募と
ティア順位の変更は、キャンペーン行を `FOR SHARE` で読み込みます: 多くのファンが互いをブロックせずに
同時に応募できますが、抽選の `FOR UPDATE` はそれらを待つ必要があり、抽選中に到着した応募は抽選を待ち、
その後キャンペーンが `drawn` になっていることを確認して拒否されます。このロックがなければ、抽選後に
エントリーが追加され、永遠に `pending` のまま残る可能性があります。統合テストでは、それぞれを実際の
Postgres に対して競合させ、ロックを取り除くと失敗することを確認しています。

一度はまった細かい点: 行がロックされる前にすでに SQLAlchemy セッションに読み込まれている場合、ロックする
クエリでは `populate_existing()` を使う必要があります。そうしないと、セッションは古いロックされていない
コピーを返し、チェックが古いデータに対して実行されてしまいます。

<a id="rules-enforced-twice"></a>
**ビジネスルールの二重強制: サービスが先、トリガーは保険。** お金や限られた座席を守るすべてのルール
（ファン限定の購入、1 公演 1 枚、チケットのキャパシティ、転売上限、抽選応募のルール）は、わかりやすい
メッセージを返せるサービスでチェックされ、さらに Postgres のトリガーでも再度チェックされるため、新しい
コード経路のバグやデータベースへの直接書き込みに対してもルールが守られます。バックエンドは各トリガーの
`RAISE EXCEPTION` のテキストを、それぞれ独自の HTTP ステータスを持つ型付き例外に変換するため、トリガーに
よる拒否は 500 ではなく、わかりやすい 400/403 としてクライアントに届きます。全一覧は
[ビジネスロジック](business-logic_JP.md#rules-and-where-theyre-enforced)にあります。

<a id="sync-handlers"></a>
**意図的な同期ルートハンドラー。** すべてのルートハンドラーは `async def` ではなく通常の `def` です。
その下のスタック — SQLAlchemy のセッション、bcrypt、PayPal の HTTP クライアント、boto3 — は同期的であり、
FastAPI は `def` ハンドラーをスレッドプールで実行するため、遅いデータベースクエリや PayPal 呼び出しが
占有するのはワーカースレッド 1 つだけです。同じコードを `async def` の中に書くとイベントループ上で実行され、
プロセス内の他のすべてのリクエストを停止させてしまいます。小規模な単体ベンチマークでは、1 秒間
ブロックする 5 つの同時リクエストが、`async def` では 5 秒、`def` では 1 秒かかりました。本当に非同期な
唯一のステップである PayPal Webhook の生ボディの読み取りは非同期の依存関係として実装され、同期ハンドラーは
それをバイト列として受け取ります。

<a id="rate-limiting"></a>
**レート制限 — Redis 上の固定ウィンドウ、意図的なフェイルオープン。**
各リクエストは、ルートのテンプレートとユーザー ID またはクライアント IP を組み合わせたキーの Redis
カウンターをインクリメントします（`INCR`、有効期限はウィンドウを作成したリクエストが設定）。Redis 自体に
到達できない場合、リミッターはログを出力してリクエストを通過させます。レート制限されたすべてのルート
（ログインを含む 62 個）で 500 を返すよりもこちらを選んでいます — 障害中にリミッターが動作することよりも
可用性のほうが重要であり、障害の原因が何であれリミッターはどのみち回避されるため、フェイルクローズに
しても実際のセキュリティは向上しません。既知の課題が 2 つあります（バックエンド `docs/bugs.md`）:
インクリメントと有効期限の設定は別々の Redis 呼び出しなので、その間でクラッシュすると期限切れにならない
カウンターが残る可能性があること（#22）、そして IP をキーにした制限は回避可能であること（#7）。Render の
リバースプロキシの背後では、接続元の生の IP はすべての訪問者について Render 自身のエッジになるため、
全員が 1 つの共有バケットにまとめられてしまいます。uvicorn の `ProxyHeadersMiddleware` は
`X-Forwarded-For` から訪問者ごとの IP を復元しますが、`trusted_hosts="*"` では、クライアントが書き込む
ヘッダーの左端のエントリーを読み取ります — そのため攻撃者は偽の値を使ってリクエストごとに新しいバケットを
作り出せてしまいます。**修正予定:** 自前のプロキシが追加したエントリー（右から数える）を読み取り、
ログイン失敗に対するアカウント単位の制限を追加します —
[`docs/plans/rate-limit-client-ip.md`](https://github.com/TranXuanAnh930/i-dolly-backend/blob/main/docs/plans/rate-limit-client-ip.md)
を参照してください。

<a id="webhooks"></a>
**Webhook の処理 — イベント ID の台帳は不要。ドメインがすでに冪等性を無償で提供しているため。**
当初の計画は、PayPal のイベント ID をキーとする `processed_webhook_events` テーブルでした。しかし
これは不要だとわかりました: `finalize_paypal_payment` が実際の処理を行うのは `payment.status == pending`
の場合のみで、支払いのステータスが `pending` から抜けるのは 1 回だけです — したがって PayPal の Webhook が
フロントエンド自身のキャプチャ呼び出しの前に来ても、後に来ても、その代わりに来ても、あるいは同じイベントが
2 回来ても（Webhook ではこれが明示的に許容されています）、その関数に到達した 2 番目の呼び出し元は必ず
pending でない支払いを見つけて何もしません。真正性は、PayPal の証明書チェックを再実装するのではなく、
イベントを PayPal 自身の verify-webhook-signature API に送り返して確認します。注文イベント
（`CHECKOUT.ORDER.*`）とキャプチャイベント（`PAYMENT.CAPTURE.*`）では注文 ID の格納場所が異なります。
ハンドラーはどちらからでも読み取り、その他のイベントには 200 で応答して、PayPal が何日もリトライし
続けないようにしています。

<a id="caching"></a>
**キャッシュ — 時間制限だけでなく書き込み時に無効化し、実際のスキーマで検証する。**
当初は 2 つの商品一覧キーだけでしたが、現在は認証不要のページ単位の読み取りと、マネージャー／管理者の
設定ページのすべてをカバーしています: ストアのグリッド、イベント／メンバー／グループのグリッド、
会場／アイドルカラーの参照、そしてマネージャーのアイドル／アイドルフォーム／グループ／イベント／商品／
商品フォームの各ページと事務所一覧 — すべて msgpack でシリアライズし 5 分の TTL を設定しており、
期限切れを待つのではなく書き込み時に無効化されます。TTL だけでもいずれは自己修正されますが、以前は
購入による `Product.quantity` の減少や、マネージャーによるグループの編集の後、実際の変更から最大 5 分間
キャッシュされたページが古いまま残っていました — これを修正するため、すべての変更系エンドポイントが
書き込みのコミット直後に、影響するキャッシュキーを明示的に削除するようにしました。この削除は、元の書き込み
自体と同じ成功条件で制御されるため、拒否された書き込みやまだ保留中の書き込みによって、実際には古く
なっていないキャッシュが無効化されることはありません。キャッシュが複数のテーブルをカバーするように
なって初めて現れる 2 つの派生的な問題があります:
- **ドメインをまたぐ無効化。** グループのキャッシュされたページには計算済みの `member_count` が含まれます。
  アイドルがそのグループに加入・脱退すると、`groups` テーブルには一切触れずにこの数が変わります。
  そのため、アイドルの書き込みはグループのキャッシュも無効化します（メンバーページのグループフィルターに
  ついてはその逆も同様）— あるキャッシュページの数値が別のテーブルの行に依存する箇所すべてに、
  同じ考え方を適用しています。
- **1 つの共有キーではなく、スコープ付きのキー。** マネージャーの商品ページは `company_id` でスコープが
  区切られています（マネージャーは自社のカタログのみを閲覧し、管理者はすべてを閲覧します）。これを 1 つの
  共有キーでキャッシュすると、ある会社のキャッシュページが別の会社のリクエストや管理者のフィルターなしの
  画面に漏れてしまいます — そのため `company_id` ごとに 1 つの Redis キーを使い、書き込み時には、ある商品の
  書き込みが実際にどのキーに影響したかを計算するのではなく、すべての会社のキーをクリアします
  （`company_id` は `Product` 自体のカラムではなく、`album_details`/`merch_details` を通じて間接的に
  解決されるため、クリアすべきキーを正確に特定するのはコストがかかります — すべてクリアするほうが安価です）。

すべてのキャッシュページは、スキーマの横に並行する別の形を手書きするのではなく、実際のレスポンス用
Pydantic モデルで検証し、*それ* をダンプして構築されます — そのため、スキーマ上でフィールド名が変更
されると、エンドポイントの `response_model` が実際に約束する内容から黙ってずれていくのではなく、次に
キャッシュが書き込まれるときに明確に失敗します。

公演詳細ページは閲覧者固有の情報を含まずにキャッシュされます。*この* ファンがすでにチケットを持っているか、
抽選に当選したか、ティアを順位付けしたかはリクエストごとに計算され、後からマージされるため、あるファンの
状態がキャッシュされて別のファンに返されることはありません。

キャッシュのコードは、インポートの循環を避けるために 2 つに分かれています: キー名と `delete_cached_*`
メソッドは Redis にのみ依存するモジュールにあり、サービスはこれをインポートして自身の処理（購入手続き、
支払い、抽選）の中で無効化を行います。ページを再構築するためにサービスを呼び出すリードスルーの
`get_cached_*` メソッドはこれを継承し、ルーターからのみ使用されます。

<a id="lottery-notifications"></a>
**抽選の通知 — 投げっぱなしのジョブに対するマネージャー向けの 3 つのシグナルと、当選／落選メールを
廃止した理由。** `PUT /concerts/lottery-draw/{id}` は Celery タスクをキューに入れてすぐに戻るだけです —
ルーターは実際の抽選結果を受け取らないため、マネージャーが抽選の進行段階を知る唯一の手段は 3 つの個別の
アプリ内通知です: `lottery_draw_triggered`（ボタンが押された瞬間）、`lottery_draw_failed`（タスクが例外を
送出した場合 — ダブルクリックによるキャンペーン終了の競合、応募がまだ締め切られていない、本物のバグなど —
例外を捕捉して通知した後に再送出するため、通知だけでなく Celery 自身の `FAILURE` 状態にも反映されます）、
そして `lottery_draw_completed`（抽選自体のコミットが完了した場合）。3 つのいずれにも当選者ごとの詳細は
含まれません — それは [抽選のユースケースフロー](use-case-flows_JP.md) の結果画面の役割です。ファンには
当選・落選どちらの場合もアプリ内の `lottery_result` 通知が届き、当選者には `lottery_payment_reminder` も
届きますが、メールは送られません: `LOTTERY_WON`/`LOTTERY_LOST` のテンプレートは初期には存在していましたが、
実際のシードファンのアドレスに対するテストで、テスト抽選のたびに本物の当選／落選メールが送られていた
ため、意図的に削除しました。`lottery_payment_confirmation`（実際の支払いの成功）はメールを残しています。
ここで本当に受信箱への通知に値するのは「抽選がどうなったか」ではなく、支払い／チケットの確認だからです。
別の話として、Celery タスクの戻り値は生の `LotteryResult` Pydantic モデルとして返すのではなく
`.model_dump(mode="json")` する必要があります — Celery の JSON 結果シリアライザーは任意のモデルを
エンコードできず、以前は生のオブジェクトを返していたために、データベース上では抽選が正常に完了して
いたにもかかわらず、実際の処理が終わった後のエンコード処理の失敗だけが原因で、Celery 自身はタスクを
`FAILURE` としてログに記録していました。

確認メールはトランザクションのコミット後にのみキューに入れられます。コミット前にキューに入れると、
購入がロールバックされたチケットについてファンにメールを送ってしまうことになります。

<a id="soft-deletes"></a>
**履歴が参照する行は論理削除。** グループとアイドルは削除せずに無効化（`is_active = false`）し、公演は
キャンセルします: チケット、抽選エントリー、公演の出演情報、商品がすべてそれらを参照しており、物理削除を
するとその履歴がカスケード削除されるか、孤立してしまいます。無効化されたアーティストは公開ページからは
消えますが、再有効化できるようにマネージャーのフォームでは引き続き読み込めます。商品はまだこのルールに
従っていません — 商品を削除すると、今でも過去の注文明細にカスケードします（バックエンド `docs/bugs.md` #2）。
