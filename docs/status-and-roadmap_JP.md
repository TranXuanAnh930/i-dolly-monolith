## 既知の制限事項

ここの要約をそのまま信じるのではなく、各サブモジュールの最新の一覧を確認してください — まずは
[`i-dolly-backend/README.md#known-limitations`](https://github.com/TranXuanAnh930/i-dolly-backend#known-limitations)、
その `docs/project_status.md`、そしてバグバックログの `docs/bugs.md` から。要するに、これは継続的な
本番トラフィックを受けるシステムではなく、ポートフォリオプロジェクトです — それを前提に扱ってください。

その一覧に埋もれさせず、ここで直接挙げておくべき具体的な課題が 1 つあります: **期限切れの未払い抽選当選
チケットを回収するジョブがありません。** 当選したものの `payment_deadline_at` までに支払わなかった
ファンの確保済み座席は、在庫に戻されるべきですが、現在これを定期的に行う処理はありません。期限は
当選者が支払おうとしたとき（`checkout_won_ticket` または PayPal 支払いの確定処理）に遅延的にチェック
されるだけで、戻ってこない当選者は座席を無期限に確保し続けます。詳細:
`i-dolly-backend/docs/project_status.md` §8。

## 検証方法

- **ユニットテスト**（440 件以上）: モックしたセッションとインメモリのフェイク Redis を使ってサービスをテスト。
- **統合テスト**（約 250 件）: 新しくマイグレーションしたテストデータベース上で、実際の Postgres と
  Redis に対して実際の HTTP スタックを実行 — RBAC と会社スコープのチェック、および 2 つのトランザクションを
  同時に実行する競合テスト（同時購入、同時抽選、抽選処理と競合する応募や順位変更）を含みます。
  競合テストは、依存しているロックを取り除くと失敗することを確認済みです。
- **CI:** `main`（および `develop`）への push とプルリクエストでリントと全テストを実行。
- **ライブチェック:** デプロイ済みドメインでの確認（証明書、リダイレクト、CORS）。

## 未解決の課題

バックエンドの [`docs/bugs.md`](https://github.com/TranXuanAnh930/i-dolly-backend/blob/main/docs/bugs.md)
で優先度順に管理しています:

| 分野 | 課題 | 状況 |
|---|---|---|
| セキュリティ | IP ベースのレート制限は偽造した `X-Forwarded-For` で回避できる（#7） | 修正予定（`docs/plans/rate-limit-client-ip.md`） |
| データ整合性 | 商品を削除すると、過去の注文からその明細が消える（#2） | 未対応 |
| 注文 | 注文をキャンセルしても在庫が戻らず返金もされない（#14）。キャンセルした注文が転売上限にカウントされたままになる（#13） | 未対応 |
| 決済 | PayPal のキャプチャが行ロックを保持したまま実行され、キャプチャは成功したがコミットされなかった場合に照合されない（#8） | 設計が必要 |
| 決済 | 放棄された PayPal 決済が有効期限なしで `pending` のまま残る: 一般販売チケットの場合はファンが再購入できなくなり（#12）、注文が履歴に溜まり（#27）、未払いの注文を発送済みにできてしまう（#26） | 保留、まとめて修正予定 |
| 耐障害性 | Redis が停止していると、キャッシュされたページが 500 を返す（#11） | 設計が必要 |
| 認証 | パスワードを変更しても他のセッションが終了しない。リセットリンクは期限切れまで再利用できる。リフレッシュトークンが平文で保存されている（#18〜#20） | 未対応 |

最近修正されたもの: 注文ごとの配送状況行の重複、他ユーザーのカート商品の削除、応募期間外の抽選応募、
抽選処理を壊していた順位変更、1 つのティアでファンが 2 回当選する問題、イベントループをブロックする
ルートハンドラー、`DEBUG` がデフォルトでオンになっていた問題、カート内価格のずれ、コミット前に
送信されていた確認メール、ハンドラーをクラッシュさせていた PayPal Webhook イベント。

## 今後の取り組み

計画済みだが未着手のもの — 推測で設計するのではなく、ここでは名前を挙げるにとどめます:

- **OLAP への移行** — `i-dolly-backend/docs/project_status.md` §5 で未着手とされている ETL／分析
  パイプライン: 各ビジネスイベント（チケット購入、抽選の応募／実施、支払い／発送状況の変更）と同じ
  トランザクション内で書き込まれるイベントソーシング型のアウトボックス（`domain_events`: type、payload、
  occurred_at、processed）を、下流で分析向けのファクトテーブル（`fact_sales_by_concert`、
  `fact_lottery_conversion`、`fact_fan_activity`）に変換します — OLTP の形がさらに固まった段階の
  スコープに応じて、同じ Postgres インスタンス内の別スキーマか、専用の OLAP ストアのどちらかにします。
- **Go によるベンチマーク** — FastAPI バックエンドに対するスタンドアロンの Go 製負荷テストツールで、
  `pytest` による正しさのみのカバレッジに頼るのではなく、実際の同時スループット／レイテンシの数値
  （購入時の在庫ロックの競合、抽選処理、バーストトラフィック下のレート制限）を得ます。未着手で、
  対象とするエンドポイントや負荷プロファイルはまだ未定です。
- **定期クリーンアップジョブ** — 上述の遅延チェックに頼るのではなく、未払いの抽選当選や放棄された
  PayPal 決済を定期的に（Celery Beat で）失効させます。
- **公演リマインダー** — チケット保有者に公演前にリマインドします。`event_reminder` 通知タイプは
  バックエンドにすでに存在しますが、まだ送信する処理はありません。近日の公演を見つけて、支払い済み
  チケットを持つ各ファンにアプリ内で（場合によってはメールでも）通知する定期ジョブが必要です。
  どれくらい前にリマインドするか、どのチャネルを使うかはまだ未定です。
- **プロジェクトドメインでのお問い合わせメール** — 問い合わせが `i-dolly-app.site` 上のアドレス
  （例: `support@i-dolly-app.site`）に届くお問い合わせフォーム。Cloudflare Email Routing はドメイン宛ての
  メールを受信・転送できますが送信はできないため、受信した問い合わせは受信箱に転送し、送信者への自動
  返信はアプリの他のメールと同様に Resend 経由で送ることになります。アドレス、フォームの項目、
  スパム対策はまだ未定です。
