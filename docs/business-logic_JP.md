# ビジネスロジック

[← README に戻る](../README.md)

汎用的な CRUD ではなく、アイドルのチケット販売プラットフォームとして成り立たせているルールです。
各ルールはまずサービス層でチェックされ、わかりやすい 400/403/404 を返します。お金や限られた座席が
関わる箇所では、Postgres のトリガーが同じルールを保険として再度強制するため、バグやデータベースへの
直接書き込みに対してもルールが守られます。バックエンドの `app/exception/db_triggers.py` が、トリガーの
`RAISE EXCEPTION` を同じ種類の HTTP エラーに変換します。トリガーのないルールは以下で
*サービスのみ* と記載しています。

詳細: [`database-design.md` §4](https://github.com/TranXuanAnh930/i-dolly-backend/blob/main/docs/database-design.md)
（RBAC、ファン限定、転売防止）と §5（抽選と購入のシーケンス図）、およびフロントエンドの
[`business_logic.md`](https://github.com/TranXuanAnh930/i-dolly-frontend/blob/main/docs/business_logic.md)。

<a id="rules-and-where-theyre-enforced"></a>
## ルールとその強制箇所

8 つのトリガー関数を、12 個のトリガーとして設定しています:

| ルール | データベースでの保険 | HTTP エラー |
|---|---|---|
| カートの利用、購入手続き、抽選への応募、チケットの保有ができるのはファンのみ | `cart`、`orders`、`lottery_entries`、`tickets` に対する `fn_enforce_fan_only_purchase` | 403 |
| 1 公演につき 1 人のファンが持てる有効なチケットは最大 1 枚 | `tickets` に対する `fn_enforce_one_ticket_per_concert` | 400 |
| 公演のチケットティアの合計は公演のキャパシティを超えられない | `ticket_types` に対する `fn_enforce_concert_ticket_capacity` | 400 |
| 転売制限対象の商品は、ファン 1 人あたり全注文を通じて最大 3 個まで | `orders_items` に対する `fn_enforce_resale_cap` | 400 |
| 抽選キャンペーンごとのファン 1 人あたりのエントリー数は最大 `max_entries_per_user`（1 に固定） | `lottery_entries` に対する `fn_enforce_lottery_entry_cap` | 400 |
| ファンは抽選に応募する前にそのティアを順位付けしなければならない | `lottery_entries` に対する `fn_require_lottery_preference` | 400 |
| 順位付けしたティアは、順位付けした公演に属していなければならない | `lottery_preferences` に対する `fn_require_ticket_type_matches_concert` | 400 |
| 商品はアルバム詳細かグッズ詳細のどちらか一方のみを持ち、両方は持たない | `album_details`、`merch_details` に対する `fn_enforce_single_product_detail_kind` | 400 |
| （公演、ティア、販売方式）ごとにチケット種別は 1 つ、冪等性キーごとに支払いは 1 つ | UNIQUE 制約（同様に変換） | 400 / 409 |

*サービスのみ*（トリガーなし）:

- 抽選への応募は、キャンペーンが `open` かつ応募期間内の場合のみ受け付けます。
- ファンのティア順位は、順位付けしたティアのキャンペーンが受付中の間のみ設定でき、応募締め切り後や
  抽選実施後は変更できません。また、すでに応募したティアを順位から外すことはできません。
- 一般販売のチケットは、そのティアの一般販売キャンペーンが受付中かつ販売期間内の場合のみ購入でき、
  ファンがその公演の抽選エントリーを未確定または当選の状態で持っている間は購入できません。
- 抽選の当選分は `payment_deadline_at`（デフォルトは 48 時間）までに支払う必要があります。期限後に
  支払おうとするとチケットは失効し、座席は解放されます。
- マネージャーは作成後に商品やチケット種別の価格を変更できません（管理者は可能）。
- 公演が販売中、売り切れ、または終了になった後は、マネージャーは日付、開場時刻、キャパシティの変更や
  チケットティアのサイズ変更ができません。公演をキャンセルするとロックが解除されます。
- グループ、アイドル、公演は削除せず、無効化またはキャンセルします。これにより、チケット、注文、
  抽選の履歴が参照を保持できます。

## ルールの詳細

- **販売経路を問わず、1 公演につきファン 1 人 1 枚。** 一般販売で購入した場合も、抽選でティアに
  当選した場合も、より良い席を狙って 2 つ目のティアに応募した場合も、ファンが特定の公演について
  同時に持てる有効なチケット（予約済み、支払い待ち、支払い済み、使用済み）は最大 1 枚です。すでに
  1 枚持っているファンは、その公演の抽選にも応募できません。
- **抽選の公平性: 順位優先、ファン 1 人 1 回、購入による倍率なし。** ファンは応募前に受け入れ可能な
  ティアを順位付けします。抽選では、公演の全ティアのキャンペーンについて第 1 希望をすべて処理してから
  第 2 希望に進むため、まだ対象となる上位のティアが確定していないうちに、下位のティアに当選することは
  ありません。同じ順位内の当選者は `random` のメルセンヌ・ツイスタではなく `secrets.SystemRandom()`
  （CSPRNG）で選ばれます — 統計的に一様なだけでなく、暗号学的にランダムです。下記の [抽選](#lottery) を参照してください。
- **転売防止の上限。** `is_resale_capped` が設定されたカテゴリ（デフォルト）では、1 人のファンが注文履歴
  全体を通じて 1 つの商品を購入できる数が 3 個に制限されます — カート側のチェックだけでなく
  `orders_items` に対するトリガーで強制されるため、通常のカートフローを経由しない購入経路でも守られます。
- **購入操作はファン限定。** カート、購入手続き、抽選への応募、チケットの直接購入は、いずれも
  マネージャー／管理者アカウントを一律に拒否します — スタッフアカウントはプラットフォームを運営する
  ためのもので、買い物をするためのものではありません。アカウントもリソースもそれ自体は完全に有効な
  ため、400（バリデーション）ではなく 403（認可）を返します。
- **共有の管理者プールではなく、会社単位の管理。** マネージャーは自社のグループ／アイドル／公演／
  チケット種別／抽選キャンペーン／商品／注文のみを閲覧・変更できます — UI で隠すだけでなく、すべての
  変更系およびマネージャー向けエンドポイントでクエリレベルの `company_id` フィルターにより強制されます。
  商品の所属会社はアルバム詳細またはグッズ詳細を通じて解決されます。どちらも持たない商品はどの
  マネージャーでも管理できます。管理者はこのスコープを完全に無視できます。
- **技術的な保証にとどまらない、ビジネス上の保証としての支払いの冪等性。** すべての購入手続きには
  クライアントが生成した冪等性キーが含まれるため、リトライされたリクエストが 2 つ目の支払いを作成する
  ことはありません。さらに、支払いが `pending` から遷移するのは 1 回だけです — フロントエンド自身の
  キャプチャ呼び出しと PayPal の Webhook のどちらが先に到達しても、2 番目の呼び出し元は pending でない
  支払いを見つけて何もしないため、リトライや重複したリクエストによってファンに二重請求したり、
  チケットを二重発行したりすることはありません。

<a id="lottery"></a>
## 抽選

1. **順位付け。** ファンは公演の抽選ティアの順位リストを提出します（`POST /lottery_preferences/set`）。
   各ティアには、応募期間が開始済みのキャンペーンが必要です。
2. **応募。** 応募期間中、ファンは順位付けしたティアの 1 つ以上に応募します — 無料で、支払いは
   不要です。`/lottery_entries/apply-batch` は複数のティアにオールオアナッシングで応募し、レート制限の
   枠を 1 つだけ消費します。
3. **抽選。** すべてのキャンペーンの応募期間が終了した後、公演の所属会社のマネージャーが抽選を実行し、
   Celery ワーカー上で処理されます:
   - 第 1 希望、第 2 希望… の順に: 座席が残っている各ティアについて、まだ当選していないファンの
     その順位の未確定エントリーを取り出し、残り座席数と同じ数だけランダムに選びます。
   - 各当選者には `pending_payment` のチケット（座席はすぐに `sold_quantity` にカウントされる）が
     発行され、支払期限は抽選から `payment_deadline_hours` 後です。
   - 残りのエントリーはすべて `lost` に、すべてのキャンペーンは `drawn` になります。
   - ファンにはエントリーごとに `lottery_result` 通知が届き、当選者には `lottery_payment_reminder` も届きます。
4. **支払い。** 当選者は期限までに `POST /tickets/{ticket_id}/checkout` で支払います。

応募と順位の変更はどちらもキャンペーン行に共有ロックを取得し、抽選は排他ロックを取得します。
そのため、抽選中に到着した応募や順位変更は待機し、その後キャンペーンが `drawn` になっていることを
確認して拒否されます。抽選が把握していないエントリーや希望順位が追加されることはありません。
統合テストでは実際の Postgres に対してこの 2 つを競合させ、これを証明しています。

## 状態遷移

| エンティティ | 状態 |
|---|---|
| 公演 | `scheduled` → `on_sale` → `sold_out` / `completed`。どの時点でも `cancelled` になり得る |
| 抽選キャンペーン | `open` → `drawn` → `completed`、または `cancelled` |
| 抽選エントリー | `pending` → `won` / `lost` |
| チケット | `pending_payment` → `paid` → `used`。`cancelled`（一般販売の支払い拒否）または `expired`（抽選当選の未払い）。管理者が手動で発行したチケットは `reserved` |
| 注文 | `pending`（PayPal のキャプチャ待ち）→ `confirmed`、または `cancelled` |
| 支払い | `pending` → `success` / `failed` |
| 配送 | `pending` → `processing` → `shipped` → `delivered`、または `cancelled` |
