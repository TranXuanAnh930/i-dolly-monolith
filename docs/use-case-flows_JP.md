# ユースケースフロー

[← README に戻る](../README_JP.md)

複数のエンドポイントにまたがる複数ステップの流れです — 各リクエストはステートレスで、以下の各ステップは
個別の HTTP 呼び出しであり、前のステップが返したトークンや ID によってのみ結び付いています。

| # | フロー | アクター |
|---|---|---|
| 1 | [パスワードを忘れた → リセット → 再ログイン](#flow-1) | ファン |
| 2 | [カートに追加 → 購入手続き → 通知](#flow-2) | ファン |
| 3 | [抽選: 順位付け → 応募 → 抽選 → 支払い](#flow-3) | ファン + マネージャー |
| 4 | [一般販売チケットの購入](#flow-4) | ファン |
| 5 | [公演の販売準備](#flow-5) | マネージャー |
| 6 | [注文の発送](#flow-6) | マネージャー |

<a id="flow-1"></a>
### 1. パスワードを忘れた → リセット → 再ログイン

1. `POST /profile/forgot-password` — メールアドレスが登録されているかどうかに関わらず常に同じ汎用的な
   メッセージを返すため、このエンドポイントをアカウントの列挙に使うことはできません。登録されている場合、
   `reset_password_process` が短期間有効な JWT リセットトークン（`EMAIL_TOKEN_EXPIRE_MINUTES`）を発行し、
   他のすべてのメールと同様に、それを含むメールを Celery（`celery_app.send_task`）経由でキューに入れます。
2. ファンがそのメール内のリンクをたどると、フロントエンドの `/reset-password` ページが開きます
   （`DEBUG=true` のローカル開発では、メールは送信されずコンソールに出力されます）。このページは
   `{token, new_password}` を付けて `POST /profile/set-password` を呼び出します。これによりアカウントの
   既存のリフレッシュトークンがすべて失効します — 攻撃者がすでに持っていたセッションが、彼らを締め出す
   ためのリセット後も生き残ることはありません — そしてアプリ内の `password_reset` 通知が書き込まれます。
3. 新しいパスワードで `POST /account/login` — 通常のログインで、新しいアクセス／リフレッシュトークンの
   ペアが発行されます。

<a id="flow-2"></a>
### 2. カートに追加 → 購入手続き → 2 つのチャネルで通知

1. `POST /cart/add_cart` — 商品の行をロックして在庫を確認し、商品の現在の価格でカートの行を追加または
   更新します。
2. `POST /order/checkout`（ユーザーごとに 60 秒あたり 3 リクエスト）— 配送先住所、想定合計金額、
   ゲートウェイ、冪等性キーを含みます。転売上限を確認し、影響を受けるすべての `Product` 行を
   （固定の ID 順で、デッドロックを回避して）ロックし、そのロック下で在庫を確認して、
   `Order`/`OrderItem`/`Payment` と注文の配送状況の行を 1 回のコミットで作成します。支払いが成功した
   場合のみ、同じコミットで在庫の減算、カートのクリア、アプリ内の `order_confirmation` 通知の書き込みも
   行います。商品一覧、ストアページ、商品詳細のキャッシュは、コミットが完了した直後に無効化されます。
3. ルーターに戻り、`checkout()` が注文を即座にキャンセルせずに返った場合（モック決済で拒否されると即座に
   キャンセルされ、その場合は確認メールは送られません）: `EmailTemplate.ORDER_PLACED` のメールが
   `celery_app.send_task(...)` 経由で、リクエスト／レスポンスのサイクルから完全に切り離して送出され、
   Celery ワーカーが処理できるタイミングで取り出されます。

PayPal の場合、キャプチャまたは Webhook が確定させるまで注文は `pending` のままです（[アーキテクチャ](architecture_JP.md#data-flow)
のチケットと同じ `finalize_paypal_payment` の経路）。在庫が減算されるのはその時点のみです。

<a id="flow-3"></a>
### 3. 抽選応募 → マネージャーによる抽選 → 当選 → 支払い → チケット入手

1. `POST /lottery_preferences/set` — ファンが公演のティアを順位付けします（第 1 希望 VIP、第 2 希望
   プレミアム、…）。順位付けする各ティアには応募期間が開始済みの抽選キャンペーンが必要で、応募締め切り後は
   順位を変更できません。
2. `POST /lottery_entries/apply`（複数ティアに一度に応募する場合は `/apply-batch`）— 無料で、カートも
   支払いも不要です。キャンペーンが受付中かつ応募期間内の場合のみ受け付けます。ファンがその公演の
   有効なチケットをすでに持っている場合や、そのティアを順位付けしていない場合は拒否されます。各エントリーは
   `lottery_registered` 通知を作成します。
3. すべてのキャンペーンの応募期間が終了した後、マネージャーが `PUT /concerts/lottery-draw/{id}` を
   呼び出します。これは RBAC の検証と `app.tasks.lottery.draw_lottery` のキュー投入のみを行います —
   実際のランクカスケード抽選は Celery ワーカー内で実行され、その公演の影響を受けるすべての
   `ticket_type`/`lottery_campaign`/`lottery_entry` 行を、いずれかに触れる前にロックします。当選すると
   `pending_payment` の Ticket 行が挿入され、お金が動く前に即座に座席が確保されます
   （`ticket_types.sold_quantity += 1`）。落選の場合は在庫には何も書き込みません。（このステップの前後で
   どの通知が発生するか、また当選／落選メールを廃止した理由については
   [エンジニアリング上の判断](engineering-decisions_JP.md#lottery-notifications)を参照してください。）
4. 抽選が完了すると、マネージャーは抽選結果画面
   （`GET /lottery_entries/concert/{concert_id}/results`）を開きます — 当選・落選を問わず、その公演の
   確定したすべてのエントリーが表示され、各行にはすでに当選者のメールアドレスとチケットの支払い状況／
   期限が含まれているため、当選者ごとに追加の呼び出しは不要です。
5. 当選者は `payment_deadline_at` までに `POST /tickets/{ticket_id}/checkout` を呼び出します —
   `Payment` が作成され、チケットが `paid` に切り替わり、続いて `lottery_payment_confirmation` の通知と
   メールが送られます。これでファンのチケットは有効になります。期限後に支払うとチケットは失効し、
   座席は解放されます。

<a id="flow-4"></a>
### 4. 一般販売チケットの購入

1. イベントページ（`GET /concerts/{id}/detail`）は公演のティアとキャンペーンを一覧表示します。
   ログイン中のファンには、すでにチケットを持っているか、抽選エントリーがあるかも表示されます。
2. チケット種別、想定金額（価格 + 10 % の税）、ゲートウェイ、冪等性キーを付けて
   `POST /tickets/checkout`（ユーザーごとに 60 秒あたり 3 リクエスト）。そのティアの一般販売キャンペーンが
   受付中かつ販売期間内であり、ティアに残席があり、ファンがその公演の有効なチケットも未確定または当選の
   抽選エントリーも持っていない場合を除き、拒否されます。
3. モックゲートウェイの場合、支払いが成功するとチケットが `paid` になり、座席がカウントされ、同じ
   リクエスト内で `ticket_confirmation` の通知とメールが送られます。支払いが拒否されるとチケットは
   キャンセルされます。PayPal の場合、キャプチャまたは Webhook が確定させるまでチケットは
   `pending_payment` のままです。
4. `GET /tickets/mine` でファンのチケットを一覧表示します。

<a id="flow-5"></a>
### 5. 公演の販売準備

マネージャーは自社の公演に対してのみこれを行えます。管理者はどの会社に対しても行えます。

1. `POST /concerts/add` — タイトル、会場、日付、開場時刻、キャパシティ（会場自体は管理者が作成します）。
2. `POST /concerts/performers/assign` — 出演するグループおよび／またはソロアイドルを登録します。
3. `POST /ticket_types/add` — ティアごとに 1 つ: ティア（VIP / プレミアム / 一般）、価格、座席数、
   販売方式（`direct` または `lottery`）。ティアの座席数の合計は公演のキャパシティを超えられません。
4. 各ティアについて、`POST /direct_sale_campaigns/add`（販売期間）または
   `POST /lottery_campaigns/add`（応募期間と時間単位の支払期限）のいずれかを実行します。
5. 抽選ティアの場合、応募期間が終了したら: 抽選を実行して結果を確認します（フロー 3、ステップ 3〜4）。
6. `GET /tickets/concert/{concert_id}/sales` で販売済みチケットを新しい順に表示します。

<a id="flow-6"></a>
### 6. 注文の発送

1. `GET /order/manager-orders-page` — マネージャーの会社の商品を含む注文を新しい順に表示し、その会社の
   明細のみを表示します。
2. `PATCH /order/{order_id}/ship` — 注文の配送状況を `pending` または `processing` から `shipped` に
   変更し、ファンに `order_shipped` 通知を送ります。マネージャーは自社の商品を含む注文のみを発送できます。

既知の課題: 発送処理はまだ注文が実際に支払われたかどうかを確認しないため、未払いの PayPal 注文を
発送済みにできてしまいます（バックエンド `docs/bugs.md` #26）。
